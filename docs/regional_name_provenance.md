# Regional name provenance

`config/name_audit.json` remains the shared, reviewed naming contract. Its
addresses describe the Japanese preservation image; its legacy identities,
evidence levels, and prose bases are not duplicated or reinterpreted for EU.
No interval translation is used to obtain European addresses.

`config/name_addresses_eu.json` freezes an explicit per-name regional inventory.
It accounts for all 15,843 origin records: 15,842 assembled EU addresses and one
source-proved Japanese-only symbol. All 1,006 audited RAM/hardware addresses
retain their exact 24-bit bus identity. The ledger binds both original ROM
sizes/SHA-256 values, and a sorted origin tuple fingerprint over current name,
normalized JP address, previous name and legacy name. Editing prose alone does
not change that identity; renaming an origin or changing its JP address does.

The ledger records each normal name as `status: assembled`, with explicit
`jp_address` and `eu_address`. Only `Reset_ChecksumLoop` may have
`status: not_assembled` and a null EU address. This is not an unknown address
or an instruction to skip provenance: the validator requires its exact JP
resolved address, its absence from the EU resolved table, and the precise
source-owned `BuildProfileEU` else branch in `src/system/boot.s`. EU instead
assembles `Reset_ChecksumUnrolledLoop`. The original `was: loc_35E` marker and
name-audit record are unchanged.

## Why the final assembler table matters

AS prints inactive conditional source rows in its listing. In EU the inactive
`Reset_ChecksumLoop` row shows the current PC `$460`, but the final symbol table
contains no such symbol. Treating that source-column PC as an EU label invents
a definition. The same issue affects JP-only exports of the EU checksum label
and `StoryText_ScanSecondAccentRun`; the latter can also hide the actual
`StoryText_AdvanceRowPointers` alias at the same JP address.

`extract_symbols.py --resolved-only` filters candidates through the final AS
symbol table **before** canonical alias selection, retaining genuine aliases.
The default extractor CLI remains the legacy implementation. In strict
verification every exported name/address must also match the resolved table;
resolved `BuildProfileJP`/`BuildProfileEU` values must identify the chosen profile.
EU always requires these checks. JP enables the additional checks with
`--resolved-exports`; its default exact-address naming audit is unchanged.

## One-time generation

Run this only after both preservation images/listings are built and verified:

```text
python scripts/derive_profile_name_addresses.py --root .
```

The producer uses the manifest-owned JP/EU listing and output paths, authenticates
both user dumps and assembled images against size/SHA-256/SHA-1/MD5/CRC32, compares
the complete ROM bytes, validates every JP origin address and both resolved
profile flags, and binds every fully printed machine-byte listing field to
the ROM. Abbreviated binary-include/EQU/conditional fields are explicitly not
treated as machine bytes. Generation provenance retains input/harness hashes
and printed-byte-row counts; these hashes document the generation inputs, not
a demand that every later listing have identical formatting.

The output is an atomic, new-only JSON file. Existing ledgers are never replaced
or automatically regenerated by runtime verification. Input changes during
derivation fail before publication. Changes to the frozen inventory or its
origin/ROM identities, missing/extra/duplicate records, arbitrary null addresses,
changed source exceptions, moved RAM, and a wrong regional export all fail closed.
Diagnostics retain the error total while printing at most twenty individual errors.

The reader parses only AS's `Symbol Table (* = unused):` section, so source
lines and comments that look like symbols are ignored.

Strict extraction produces 16,080 JP and 16,086 EU canonical addresses, including
the same 1,042 canonical RAM/hardware addresses and 35 mandatory contract symbols.
JP loses the inactive checksum entry but recovers the genuine story alias at
`$59A8`; that address is retained. Both strict gates passed. Giving the JP export
to the EU check fails with 12,852 errors, of which twenty are printed.

## Verification interface

The public `make verify-symbols PROFILE=jp` and `PROFILE=eu` enable strict
resolved exports, retaining the JP default `logs/symbols.txt` and writing EU
to `logs/symbols_eu.txt`. EU also prepares the JP origin listing through its
own JP assembler invocation, never by reusing EU profile flags.

EU needs the JP origin listing as independent evidence for the one excluded name:

```text
python scripts/verify_symbols.py --profile eu \
  --profile-address-map config/name_addresses_eu.json \
  --origin-listing build/main.lst \
  --symbols logs/symbols_eu.txt --listing build/eu/main.lst \
  --name-audit config/name_audit.json --layout config/rom_layout_eu.json \
  --runtime config/runtime_scenarios.json
```

`--profiles` defaults to `config/rom_profiles.json`; `--root` defaults to the
current repository directory for the source exclusion proof. A strict JP gate
uses its normal JP symbol/listing/layout paths plus `--resolved-exports`.
Address validation compares the current EU resolved symbols with the already
frozen ledger, not a new map derived from the listing being checked. It proves
regional address/provenance consistency, not additional semantic confidence
or runtime fidelity of the renamed game routines.
